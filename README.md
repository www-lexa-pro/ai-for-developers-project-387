## Стек

Go + Gin; TypeScript + React + Vite + Mantine.
API: TypeSpec → OpenAPI 3.0 → Hey API SDK и oapi-codegen для Go.

## Установка

Нужны Git, curl и mise 2026.11.7: https://mise.jdx.dev/getting-started.html.
После установки mise активируйте его по инструкции для своей оболочки.

```bash
git clone https://github.com/www-lexa-pro/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run setup
```

Версии инструментов закреплены в mise.toml, зависимости — в package-lock.json
и backend/go.mod/go.sum. Для обхода уязвимой транзитивной зависимости генератора
SDK закреплён js-yaml 4.3.2 через npm overrides.

Публичное приложение первого проекта: [cal-hexlet.onrender.com](https://cal-hexlet.onrender.com).

## Использование

```bash
mise run dev
```

Откройте http://127.0.0.1:5173. Главная загружает каталог из API: название,
описание и длительность типов встреч. Выбор открывает страницу типа;
её адрес можно открыть напрямую. При ошибке чтения доступна кнопка «Повторить».
Ссылка «Для владельца» открывает `/owner`: предстоящие встречи, список типов и форму создания.
Встречи всех типов показаны по Москве, ближайшие первыми; начавшиеся исключены.
Список обновляется каждые 30 секунд, при возврате на вкладку и вручную.
При сбое прежние данные остаются видимыми с предупреждением.
Новый тип сразу доступен гостям. После неизвестного результата можно проверить
список без повторного создания. Гость выбирает свободную дату и время по Москве,
вводит имя и email и нажимает «Записаться». Подтверждение показывает точные
данные встречи; письма не отправляются. Имя и email сохраняются до окончания
текущего процесса записи, а перезагрузка очищает ввод. При неизвестном результате
сервер мог сохранить запись: обновите календарь и выберите время заново;
автоматических повторов отправки нет.
Бекенд: http://127.0.0.1:8080/api/health. Ответ: `{"status":"ok"}`.
Vite передаёт запросы `/api` бекенду.

Типы и бронирования хранятся только в памяти одного экземпляра приложения. При перезапуске
данные сбрасываются: бронирования и добавленные типы исчезают, создаются «Знакомство» (15 минут), «Консультация»
(30 минут) и «Подробный разбор» (60 минут) с новыми случайными идентификаторами.
Старые ссылки становятся недействительными. Авторизации в учебном проекте нет;
страница владельца доступна всем, кто знает адрес; данные гостей
также доступны без входа.

При работе на NAS адреса относятся к NAS. Для браузера на другом компьютере
используйте SSH-перенаправление порта 5173; публичный доступ не включается.
Например: `ssh -N -L 5173:127.0.0.1:5173 <ваш-SSH-хост>`.

| Команда | Назначение |
| --- | --- |
| `mise run status` | Состояние серверов |
| `mise run logs` | Сообщения серверов |
| `mise run stop` | Остановить серверы проекта |
| `mise run generate` | Пересоздать OpenAPI, SDK и серверные типы |
| `mise run lint` | Линтеры и форматирование |
| `mise run test` | HTTP-тесты API, дымовой тест процесса, тесты интерфейса и полный путь в Chromium |
| `npm run test:e2e` | Настоящие Go/Vite и Chromium, отдельные порты 18080/15173 |
| `mise run build` | Сборки в backend/bin и frontend/dist |
| `mise run check` | Все проверки, включая типы и актуальность генерации |

Перед первым запуском браузерных проверок установите Chromium:
`npm exec playwright install -- --with-deps chromium`. В CI установка входит
в check.yml. Проверка сама запускает и останавливает собственные серверы;
порты 18080/15173 должны быть свободны. Для артефактов задайте
`CAL_TEST_ARTIFACTS=/путь/к/временной/папке`; по умолчанию используется
системная временная папка.

Серверы продолжают работать после завершения команды dev. Для daemons mise
используется pitchfork; экспериментальный режим включён только в проекте.
После изменения кода Go перезапустите бекенд:
`mise daemons restart backend`. Vite обновляет интерфейс автоматически.

hk запускает быстрые проверки изменённых файлов перед коммитом, commitlint
проверяет сообщение, перед push выполняются все проверки. Хуки не исправляют
файлы автоматически. Формат коммитов: `feat: добавить каркас сервера`.

Собственный workflow check.yml запускает проверки на каждый push и для PR
из внешних репозиториев; внутренние PR уже проверяются событием push.
Проверка Хекслета сохранена отдельно. Зелёный локальный check не подтверждает
успешный запуск GitHub Actions.

Выпуск общей версии Go + React: [release-please и проверка релиза](docs/releasing.md).

## Codex в GitHub Issues

Workflow **Codex в GitHub Issues** запускает автотриаж при открытии нового
issue автором `www-lexa-pro`. Codex берёт заголовок и описание на момент
открытия, сверяет обращение с приложением, задаёт
уточняющие вопросы при необходимости и предлагает следующий шаг. Разбор
появляется комментарием в исходном issue со ссылкой на прогон во вкладке
**Actions**. Автотриаж пропускает обращения от ботов и недоверенных авторов,
а также issue с меткой `ready-for-agent` на момент открытия.

Ручной вызов работает на новом комментарии к открытой задаче. Команду может
отправить `www-lexa-pro`. Комментарии ботов, правки комментариев и комментарии
к pull request пропускаются.

| Команда | Результат |
| --- | --- |
| `/codex explain this issue` | Объясняет задачу с учётом описания и комментариев |
| `/codex check setup` | Называет трекер, доступные скиллы и команду проверок |

Для ручного запроса начните новый комментарий с `/oc`, поставьте пробел и
напишите поручение. Регистр префикса и диагностических команд не важен.
Для обеих команд из таблицы подходит и префикс `/oc`. Новые запросы
выполняются с учётом описания задачи и обсуждения. Codex читает репозиторий
в режиме только для чтения.

```text
/oc разбери это обращение по скиллу triage. Проверь, есть ли у записи тема звонка и где она сейчас отображается. Если нужны уточнения, задай вопросы здесь. Код пока не меняй.
```

Workflow использует официальный Codex
GitHub Action с моделью `gpt-5.4-mini` и секретом `OPENAI_API_KEY`.
Для этого способа достаточно GitHub Actions, установка OpenCode GitHub App
не требуется. Checkout берёт код основной ветки. Codex читает настройки
и скиллы из репозитория и возвращает текст, который публикуется в Issue.

Ответ появляется в обсуждении задачи. В конце ответа есть ссылка на конкретный
прогон. Все прогоны доступны на вкладке
[Actions](https://github.com/www-lexa-pro/ai-for-developers-project-387/actions/workflows/codex-issue.yml).
Публичные ссылки на сессии (`share`) отключены. Следующий вызов читает историю
обсуждения повторно. На ответ и публикацию отведено по 10 минут. Ручные
вызовы модели выполняются по одному, автотриаж ставится в очередь по номеру issue.

### Проверка в GitHub

После слияния откройте новое issue от `www-lexa-pro` без метки
`ready-for-agent` и проверьте, что в обсуждении появился разбор с предложением
следующего шага. Откройте ещё одно issue с этой меткой и проверьте во вкладке
**Actions**, что запуск Codex и публикация пропущены.

После слияния откройте [issue №5](https://github.com/www-lexa-pro/ai-for-developers-project-387/issues/5)
и отправьте новый комментарий:

```text
/oc to-spec
```

Перейдите по ссылке из ответа Codex. В отдельном issue должны быть основной,
негативный и соседний сценарии, критерии проверки и ссылка на исходное
обращение. Затем отправьте в исходном обсуждении ещё один комментарий,
подставив ссылку на опубликованную спецификацию:

```text
/oc to-tickets https://github.com/www-lexa-pro/ai-for-developers-project-387/issues/<номер-спецификации>
```

Проверьте ссылки в ответе, дочерние тикеты спецификации, ссылки на исходное
обращение, метку `ready-for-agent` и зависимости между тикетами. Без доступной
ссылки на спецификацию этого workflow ответ попросит её уточнить. Повторите
команды и убедитесь, что workflow вернул ссылки на те же issue. При частичном
сбое отчёт перечислит подтверждённые публикации. Повтор команды продолжит
публикацию по сохранённому плану.

```bash
docker build -t cal:docker-local .
docker run --rm -p 127.0.0.1:18081:8080 cal:docker-local
# Другой внутренний порт:
docker run --rm -e PORT=9090 -p 127.0.0.1:18081:9090 cal:docker-local
```

Откройте http://127.0.0.1:18081 на NAS. Контейнер сам запускает Go,
который отдаёт интерфейс и API. PORT имеет приоритет над APP_ADDR;
без PORT сохраняется адрес разработки из APP_ADDR (по умолчанию 127.0.0.1:8080).
В образе PORT=8080, STATIC_DIR=/app/public — каталог собранного интерфейса.
Данные хранятся в памяти и сбрасываются после перезапуска.
Браузерная проверка уже запущенного контейнера:
`CAL_E2E_URL=http://127.0.0.1:18081 npm run test:e2e`.

## Автоматическое ревью PR

Workflow «Авторевью календаря» запускается по `pull_request` при открытии,
повторном открытии, добавлении коммита или смене целевой ветки. Он допускает
только PR из веток этого репозитория. Автор PR и инициатор события должны
быть владельцем репозитория или входить в список доверенных. Для дополнительных
людей задайте в Actions переменную `PR_REVIEW_TRUSTED_USER_IDS` с числовыми
ID пользователей через пробел. Для агента с GitHub App задайте
`PR_REVIEW_APP_BOT_ID` с числовым ID бота, под которым приложение открывает PR.
Если агент действует от имени владельца через `gh`, отдельный ID не нужен.

Ревьюер читает `REVIEW.md` из базового коммита PR и получает diff между
точными коммитами. В описании PR укажите `Refs #номер`. Ревьюер следует
ссылкам `Part of` и «Исходное обращение», получает комментарии доверенных
людей о согласовании и статусы CI для SHA ветки PR. В ответе он отмечает
недоступный контекст и ещё не завершённые проверки.

Код PR используется только как текст. В рабочую папку checkout загружает
основную ветку, из которой запускается сборщик контекста. Само определение
workflow для `pull_request` GitHub берёт из результата слияния. Поэтому
доверие к авторам внутренних веток необходимо и для изменений workflow.

Новый коммит или смена цели отменяет старый прогон. Перед публикацией
сверяются SHA ветки PR, имя и SHA целевой ветки. Codex получает существующий
секрет `OPENAI_API_KEY` и работает 10 минут в режиме только для чтения.
Отдельное задание с правом записи review публикует замечания, SHA и ссылку
на прогон. Его тайм-аут — 2 минуты.

### Когда PR открывает агент внутри Actions

Владелец регистрирует приватное GitHub App и устанавливает его только в этот
репозиторий. Права репозитория для приложения — **Contents: Read and write**
и **Pull requests: Read and write**. В настройках Actions сохраните Client ID
в переменной `PR_AUTHOR_APP_CLIENT_ID`, а приватный ключ — в секрете
`PR_AUTHOR_APP_PRIVATE_KEY`. Ключ передаётся только доверенному workflow автора.

В workflow автора получите токен установки, а затем используйте выход
`steps.pr-author.outputs.token` как `GH_TOKEN` для `gh pr create` и как
учётные данные для `git push`. Если checkout сохранил встроенный токен,
отключите его через `persist-credentials: false` и настройте HTTPS через
`gh auth setup-git` с токеном приложения перед push.

```yaml
- name: Получить токен автора PR
  id: pr-author
  uses: actions/create-github-app-token@f418cff399f7aef4c2f0ad47e25ca7a6abbdd6fc # v3
  with:
    client-id: ${{ vars.PR_AUTHOR_APP_CLIENT_ID }}
    private-key: ${{ secrets.PR_AUTHOR_APP_PRIVATE_KEY }}
    permission-contents: write
    permission-pull-requests: write
```

События от токена GitHub App запускают обычное авторевью. При использовании
встроенного токена автора GitHub может потребовать вручную разрешить запуск.
[Документация GitHub о токенах и событиях](https://docs.github.com/en/actions/concepts/security/github_token).

### Команда `/oc` в pull request

В открытом PR из ветки этого репозитория владелец `www-lexa-pro` может
написать новый комментарий `/oc <запрос>` в обсуждении или у строки diff.
Воркфлоу отвечает в обсуждении. На один PR даётся три попытки суммарно.
Перед Codex воркфлоу занимает один из трёх Git-тегов
`codex-pr-budget/<номер PR>/<слот>`. Новый коммит, отмена или тайм-аут
после резервирования бюджет не восстанавливают. Для повторной попытки
выбирайте **Re-run all jobs**. Повтор только задания Codex пропустит
вызов, поскольку допуск выдан для другой попытки Actions.
При исчерпании бюджета бот публикует `limit_exhausted`, SHA головы PR и
ссылку на лог попытки. Не удаляйте теги счётчика.

GitHub Actions принимает `issue_comment: created` для обсуждения и
`pull_request_review_comment: created` для строк diff. Оба события
проверяют один счётчик. Скрипт резервирования читается из `main`,
ключ модели — из существующего секрета `OPENAI_API_KEY`.
Для построчного события GitHub выбирает определение воркфлоу из
результата слияния PR. Изменения YAML в ветке PR могут повлиять
на выполнение ещё до мержа.

После появления воркфлоу на `main` проверьте на отдельном PR, что один
запрос из обсуждения, один построчный запрос и **Re-run all jobs**
используют три общих слота. Четвёртый запрос должен завершиться с
`limit_exhausted` и пропущенным заданием Codex. На другом PR отмените
прогон после резервирования и проверьте, что слот занят. Аналогично
проверьте тайм-аут допущенного задания.

### Реализация и публикация по спецификации

Команда `/oc implement-spec #10` в issue #5 доступна владельцу
`www-lexa-pro`. Воркфлоу сверяет заголовки и описания #10–#13
с версией из согласования и проверяет зависимости. Затем переносит
коммит #11 из PR #17, поручает Codex изменения для #12 и #13 и
запускает `mise run check` на итоговом коммите.

После успеха отдельное задание из `main` получает токен `hexlet-ai`
в окружении `implement-publish`. Используются переменная
`IMPLEMENT_APP_CLIENT_ID`, секрет окружения `IMPLEMENT_APP_PRIVATE_KEY`
и переменная `PR_REVIEW_APP_BOT_ID`. Приложение публикует ветку
`implement/spec-10` и открывает PR в `main`. В описании есть ссылки
на требования, согласование, проверенный SHA и прогон Actions.
Повторный запуск ищет PR по исходной ветке и возвращает его ссылку,
если цель по-прежнему `main` и текущий SHA совпадает с записанным
в описании результатом проверки. При смене цели или SHA запуск
сообщает причину остановки в логе и не создаёт второй PR. Если push прошёл,
а PR создать не удалось, повторный запуск снова проверяет опубликованный
коммит и завершает публикацию. Итог появляется в #5.

Локальная проверка маршрута и согласования без Codex и GitHub
выполняется командой `python3 scripts/check-implement-spec.py`.
После разрешённого запуска проверьте в Actions отдельно реализацию
и публикацию, затем сравните SHA из описания PR с SHA ветки и
убедитесь, что автор PR — `hexlet-ai[bot]`.
